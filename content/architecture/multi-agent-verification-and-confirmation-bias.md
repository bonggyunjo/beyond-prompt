## 1. 역할 분리(독립 세션)의 이유와 남는 의문

구현을 담당하는 에이전트와 별개로 테스트·검증을 담당하는 에이전트를 두는 구조는 꽤 합리적인 접근이라고 생각한다. 각 에이전트가 <strong>독립적인 세션(컨텍스트)</strong>을 가지기 때문이다.

한 세션 안에서 구현부터 테스트까지 한 번에 처리하면, 에이전트가 자신이 작성한 코드의 의도와 가정에 갇히는 <strong>확증 편향(Confirmation Bias)</strong>이 생기기 쉽고 앞선 시행착오가 컨텍스트를 흐리게 만든다. 반면 새 세션에서 출발하는 테스트·검증 에이전트는 구현 과정의 변명을 모르는 백지상태에서 결과물만 놓고 보기 때문에 상대적으로 더 객관적인 시선으로 빈틈을 짚어낼 가능성이 높다.

하지만 여기서 자연스럽게 하나의 의문이 들었다.

> **"세션을 분리해서 정밀해졌다고는 하는데, 에이전트가 '검증 완료'라고 보고한 결과가 실제로 믿을만한 테스트와 검증인지 내가 어떻게 알 수 있을까?"**

정해진 정답이 있는 영역은 아니고 사람마다 활용하는 방식도 다양하지만, 결국 테스트·검증 에이전트 역시 LLM이기 때문에 단순히 세션을 분리했다는 사실만으로는 신뢰성이 자동으로 보장되지 않는다고 본다.

## 2. 믿을만한 테스트·검증인지 판단하기 위해 살펴보는 5가지 기준

기본적으로 에이전트도 테스트를 지시하면 아래 다섯 가지 요소를 어느 정도 스스로 수행하긴 한다. 다만 내가 직접 에이전트를 다뤄보며 느낀 점들을 바탕으로, 검증 에이전트의 보고를 그대로 믿기보다 아래 기준들이 제대로 지켜졌는지 함께 짚어보는 편을 추천한다.

### ① 요약 문장이 아니라 실제 실행 증거(Command & Exit Code) 확인하기
*"단위 테스트와 통합 테스트를 모두 통과했습니다"*라는 텍스트 요약만으로는 판단하기 어렵다. **실제로 어떤 테스트 명령어를 실행했는지, 종료 코드(Exit Code)가 정상(`0`)인지, 전체 몇 개 중 몇 개가 통과했고 스킵(`Skipped`)되거나 완화된 검증 조건은 없었는지** 원시 실행 로그를 함께 남기도록 유도하는 편이 좋다.

### ② '구현 코드'가 아니라 '요구사항 명세(Spec)'를 기준으로 테스트하기
검증 에이전트에게 구현 코드만 던져주고 *"이 코드 테스트해 줘"*라고 하면, 구현 코드의 현재 동작(심지어 버그까지)을 정답으로 삼아 테스트를 끼워 맞출 위험이 있다. 개인적으로는 구현 코드가 아니라 <strong>처음 합의한 요구사항 명세(PRD, API 스펙, 수용 기준)</strong>를 기준으로 테스트 케이스를 먼저 도출한 뒤 구현과 대조하도록 방향을 잡는 편이 훨씬 낫다고 느꼈다.

### ③ 정상 케이스(Happy Path) 외에 실패·경계값 케이스 포함하기
정상 입력 1~2건만 통과하는 테스트로는 충분한 확신을 얻기 어렵다. 빈 값/`null`, 경계값, 권한 오류, 예외가 발생해야 정상인 실패 시나리오가 검증 목록에 들어 있는지 살펴보는 편이 좋다. 특히 버그 수정 작업이라면 **수정 전 상태에서 테스트가 실제로 실패(Red)하는지 먼저 확인하고, 수정 후 통과(Green)로 바뀌는지** 거치는 흐름을 추천한다.

### ④ `Mock` 사용 범위의 경계 살펴보기
에이전트는 테스트 통과를 쉽게 만들기 위해 DB, 외부 연동, 핵심 의존성까지 과도하게 `Mock`으로 대체하려는 경향을 보이곤 한다. 전부 Mock으로 돌리면 실제 SQL 오류나 직렬화 문제, 트랜잭션 설정 누락은 걸러내기 어렵기 때문에, **어디까지를 Mock으로 두고 어디를 실제 통합 환경에서 검증했는지** 리포트에 구분해 달라고 요청하는 것이 도움이 된다.

### ⑤ '구현 코드 전체'보다 '검증 체크리스트 + Diff' 위주로 검수하기
검증 에이전트가 뽑아낸 **테스트 시나리오 목록**만 사람이 훑어봐도 이 검증이 꼼꼼한지 대충 넘어갔는지 어느 정도 감이 온다. 조금 더 확실히 확인하고 싶을 때는 코드에 의도적으로 작은 버그를 하나 심어두고 검증 에이전트가 실제로 잡아내는지 확인해 보는 방식(변이 테스트 관점)도 꽤 유용하다.

## 3. 결국 핵심은 '사람의 테스트 코드 검수'와 '회귀 테스트' 축적이다

앞선 기준들을 여러 번 돌려보면서 문득 든 생각은, **각 언어와 프레임워크의 테스트 도구(`JUnit`, `Jest`, `pytest` 등)를 활용해 좋은 테스트 코드를 한 번 잘 구성해 두면 그다음부터는 생각보다 크게 문제 될 일이 없다**는 점이다.

에이전트가 테스트를 실행할 때는 결국 그 테스트 코드의 검증 로직을 그대로 돌려 결과만 확인하기 때문이다. 즉, 테스트 실행 자체보다 <strong>"애초에 그 테스트 코드 자체가 올바르게 짜여 있는가?"</strong>가 신뢰도의 9할을 결정한다. 따라서 내가 느끼기에 가장 현실적인 역할 분담은 다음과 같다.

1. **사람이 직접 테스트 코드의 정확성을 확인한다**: 구현 코드 전체를 한 줄씩 검수하기보다, 에이전트가 작성한 테스트 코드가 내가 의도한 스펙과 검증 조건(Assertion)을 정확히 찌르고 있는지 사람이 직접 한 번 확인하는 과정이 필요하다.
2. **일회성으로 버리지 않고 회귀 테스트(Regression Test)로 축적한다**: 한 번 검증을 통과한 테스트 케이스를 그 작업 끝으로 버리지 않고 프로젝트의 회귀 테스트 스위트로 계속 남겨두는 편이 바람직하다. 이렇게 쌓인 테스트를 바탕으로 **단위 테스트 진행 후 통합 테스트까지 연달아 실행**하면, 이후 기능이 추가되거나 수정될 때도 대부분의 오류는 이 과정에서 걸러진다고 본다.
3. **기존 회귀 테스트는 임의로 고치지 못하게 보호한다**: 다만 한 가지 주의할 점은, 나중에 다른 기능을 수정하던 에이전트가 기존 회귀 테스트가 깨졌을 때 구현을 고치는 대신 테스트 코드의 기대값을 몰래 바꿔 통과시켜 버릴 수 있다는 것이다. 이미 검증된 회귀 테스트는 임의로 수정·삭제·스킵하지 못하도록 기준을 세워두면 훨씬 안전하다.

## 4. 일회성 프롬프트로 끝나지 않으려면: 계층적 `.md` 문서 구조 활용하기

위와 같은 기준들을 머리로만 기억하고 매번 채팅창에 길게 프롬프트로 적어주는 방식은 금방 지치기 쉽다. 특히 검증 에이전트를 **독립적인 새 세션**으로 띄우면 이전 대화에서 내가 강조했던 테스트 기준을 전혀 기억하지 못한 채 기본 상태로 출발하게 된다.

그래서 내가 체감상 가장 추천하고 싶은 방식은, **계층적 문서 구조 안에 테스트·검증 전용 `.md` 파일(예: `docs/testing-policy.md` 또는 계층별 `AGENTS.md` 규칙)을 두고, 에이전트가 검증 단계에 들어갈 때마다 해당 문서를 읽고 정해진 절차대로 수행하도록 흐름을 잡아두는 것**이다.

```text
[계층적 문서 구조 예시]
├── Root 지침 (AGENTS.md / 시스템 규칙)
│     └─ "구현 완료 후 독립 검증 단계로 넘길 때, 테스트 관련 .md 문서를 먼저 읽고 절차를 따를 것"
│
└── 테스트·검증 규칙 문서 (test-guide.md / verification.md)
      ├─ 1. 구현 코드가 아닌 요구사항(Spec) 기준으로 테스트 시나리오 작성
      ├─ 2. Happy Path + 실패/경계값 케이스 포함 여부 점검
      ├─ 3. Mock 사용 범위 명시 및 단위 -> 통합 테스트 순차 실행
      ├─ 4. 기존 회귀 테스트 임의 수정/스킵 금지 및 신규 테스트 회귀 자산 편입
      └─ 5. 실제 실행 명령어, 통과/실패 건수, Exit Code 원시 결과 보고
```

물론 에이전트를 활용하는 정답이 하나로 정해져 있는 것은 아니지만, 이렇게 **테스트 관련 `.md` 파일을 계층 구조 속에 배치하고 각 테스트·검증 프로세스 절차를 문서대로 따라가게 구성**해 두면, 매번 사람이 똑같은 지시를 반복하지 않아도 어떤 세션의 에이전트가 들어오든 내가 기대하는 기준에 가까운 검증 결과를 얻을 수 있다고 본다.
