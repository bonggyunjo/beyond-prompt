1. 옵시디언(Obsidian)이란 무엇이며, 왜 에이전트와 함께 쓸까?#

옵시디언(Obsidian)은 클라우드 서버에 데이터를 저장하는 일반 웹 노트 앱(노션 등)과 달리, 내 컴퓨터 로컬 폴더에 저장된 순수 마크다운(.md) 파일들을 그대로 읽어 화면에 보여주고 연결해 주는 로컬 지식 관리 도구다.

처음에는 일반 메모장이나 노션과 무엇이 다른지 헷갈릴 수 있지만, AI 에이전트와 함께 개발할 때 옵시디언을 쓰는 이유는 매우 분명하다.

  1. 로컬 .md 파일과의 일체형 구조 (사람과 에이전트의 공용 작업대): 에이전트는 웹 브라우저를 뒤지는 것보다 내 로컬 폴더 안의 .md 파일을 직접 읽고 수정하는 데 훨씬 빠르고 정확하다. 옵시디언은 그 로컬 .md 파일들을 그대로 띄워주는 뷰어 겸 에디터 역할을 하므로, 사람은 깔끔한 노트 화면으로 보고 에이전트는 원본 텍스트 파일을 바로 읽고 쓰는 공용 공간이 된다.
  2. 여러 프로젝트를 잇는 중앙 허브 (SSOT) 및 지식 재사용: 백엔드 코드 저장소와 프론트엔드 코드 저장소가 나뉘어 있어도, 두 저장소가 하나의 옵시디언 보관함(Vault)을 함께 바라보게 구성하면 문서의 단일 진실 공급원(SSOT)이 만들어진다. 또한 프로젝트가 하나 끝나더라도 그 과정에서 쌓은 기술 노트와 트러블슈팅 경험, 에이전트 작업 규칙을 다음 프로젝트에서 그대로 재사용할 수 있다.
  3. 세션이 바뀌어도 유지되는 기억과 토큰 절약: 새 채팅 세션을 열 때마다 프로젝트 배경을 길게 다시 설명할 필요 없이, 잘 나뉜 옵시디언 문서 중 지금 작업에 필요한 .md 파일만 에이전트가 골라 읽게 만들 수 있다.

2. 효율적인 폴더 구조: 공통 참조 / 프로젝트 / 트러블슈팅 나누기#

옵시디언 보관함(Vault) 안에 모든 파일을 섞어두면 사람도 찾기 어렵고 에이전트도 엉뚱한 문서를 읽게 된다. 개인적으로는 역할에 따라 공통 참조 영역, 개별 프로젝트 영역, 트러블슈팅·기록 영역으로 폴더를 나누어 관리하는 구조를 추천한다.

workspace/
├── my-backend-repo/               # 백엔드 코드 레포 (AGENTS.md 포함)
├── my-frontend-repo/              # 프론트엔드 코드 레포 (AGENTS.md 포함)
└── obsidian-vault/                # 공용 옵시디언 보관함
    ├── AGENTS.md                  # 보관함 전체 규칙 및 문서 안내판
    ├── 00_Inbox/                  # 미분류 임시 메모
    ├── 10_Projects/               # [프로젝트별 격리 공간]
    │   └── roomora/
    │       ├── activeContext.md   # 현재 세션 인수인계서 (가장 최신 상태)
    │       ├── 00_MOC/            # 프로젝트 전체 문서 목차 (지도)
    │       ├── 01_Core_Rules/     # 아키텍처, ERD, 테스트 전략, UI 디자인 시스템
    │       ├── 02_Specs/          # 도메인별 기능 명세 (REQ-001...)
    │       └── 04_Logs/           # 프로젝트별 트러블슈팅(ERR) & 의사결정(DEC)
    ├── 20_Knowledge_Base/         # [공통 기술 참조] Spring, DB, Frontend 등 재사용 지식
    ├── 30_Agent_Playbooks/        # [공통 규칙] 코드 리뷰, 테스트 검증, 세션 종료 절차서
    └── 90_Templates/              # 신규 프로젝트·트러블슈팅 작성용 표준 양식

각 폴더의 역할과 사용 시점#

폴더 구분역할언제 읽고 언제 쓰는가?
10_Projects/<프로젝트>/특정 프로젝트의 설계, 기능 스펙, 현재 진행 상태 보관해당 프로젝트 작업 시작 시 목차(00_MOC)와 activeContext.md를 읽고, 기능 구현 시 관련 스펙만 골라 읽음
04_Logs/ (트러블슈팅)해결한 버그의 원인·해결책(ERR), 아키텍처 선택 이유(DEC) 기록비슷한 에러가 다시 터졌을 때 참고하고, 새로운 버그를 해결한 직후에 기록을 추가
20_Knowledge_Base/ (공통 참조)프로젝트가 끝나도 남는 범용 기술 지식 및 패턴 보관여러 프로젝트에서 공통으로 마주치는 기술 스택 개념·설정법을 참고할 때 열람
30_Agent_Playbooks/ (공통 규칙)테스트 검증 절차, 코드 리뷰 기준, 세션 인수인계 규칙모든 프로젝트에서 에이전트가 검증이나 마감 단계를 밟을 때 공통 지침으로 열람
90_Templates/새 문서 생성 시 형식을 맞추기 위한 빈 양식 모음새 프로젝트나 트러블슈팅 문서를 만들 때 복사해서 사용

3. 폴더별 권한(Read / Write)은 어떻게 주는 게 좋을까?#

옵시디언 문서에 에이전트 권한을 줄 때 모든 폴더를 마음대로 수정하게 두는 것은 위험하다. 작업 도중 에이전트가 핵심 아키텍처 원칙이나 공통 규칙 문서를 임의로 고쳐버릴 수 있기 때문이다. 따라서 폴더의 성격에 따라 권한 기준을 나누어 지시해 두는 편이 안전하다.

  1. 읽기 전용 (Read-Only) — 공통 규칙 및 핵심 설계: 30_Agent_Playbooks/나 프로젝트의 01_Core_Rules/(ERD, 아키텍처, UI 디자인 시스템 등)는 사람이 직접 합의한 기준이므로 에이전트가 임의로 수정하지 못하고 읽기만 하도록 제한한다. (수정이 꼭 필요하다면 먼저 사람에게 제안하고 승인을 받게 한다.)
  2. 추가 전용 (Append-Only) — 트러블슈팅 및 의사결정 로그: troubleshooting.md, decisions.md 같은 기록 문서는 과거 이력을 지우거나 덮어쓰지 않고, ERR-001, DEC-001처럼 번호를 매겨 아래로 계속 누적(Append)하도록 규칙을 둔다.
  3. 갱신/덮어쓰기 허용 (Read & Overwrite) — 현재 상태 인수인계서: activeContext.md처럼 *“지금 어디까지 했고 다음에 무엇을 해야 하는가”*를 담는 파일은 작업이 끝날 때마다 이전 내용을 비우고 최신 상태만 깔끔하게 덮어쓰도록(Overwrite) 허용한다.

4. AGENTS.md에는 어떤 내용이 들어가야 할까?#

AGENTS.md는 에이전트가 작업을 시작할 때 가장 먼저 읽는 안내판 겸 헌법이다. 모든 문서 내용을 AGENTS.md 하나에 다 우겨넣으면 컨텍스트가 너무 무거워지므로, 아래 4가지 핵심만 간결하게 적어두는 것을 추천한다.

  1. 보관함(또는 프로젝트)의 정체성과 경로: 이 프로젝트가 무엇인지 2~3줄 요약과 옵시디언 문서 폴더의 상대 경로(예: ../obsidian-vault/10_Projects/roomora/)
  2. 필수 선행 열람 순서 (라우팅 표): *“세션을 시작하면 activeContext.md와 목차를 먼저 읽고, 백엔드 작업이면 A 문서를, 테스트할 때는 B 문서를 읽어라”*처럼 상황별로 어떤 .md를 찾아 읽어야 하는지 안내
  3. 폴더별 권한 및 작성 규칙: 어디는 읽기 전용이고 어디에 트러블슈팅을 누적하는지, 파일명은 영문 snake_case.md를 쓰고 표준 마크다운 링크를 사용하라는 규칙
  4. 작업 종료 시 마감 절차 (Session Handoff): 기능 하나가 끝나면 ① 바뀐 스펙을 문서에 반영하고, ② 해결한 이슈를 트러블슈팅 로그에 추가한 뒤, ③ activeContext.md를 50줄 이내로 최신화하고 끝내라는 마감 루프

5. 배워가며 체감한 옵시디언 효율적 활용 팁 4가지#

아직 옵시디언을 하나씩 익혀가는 단계에서, 에이전트와 함께 쓸 때 특히 챙기면 좋은 팁 네 가지를 정리해 보았다.

  1. 옵시디언 설정에서 Wikilinks 끄기 (가장 중요): 옵시디언은 기본적으로 [[문서이름]] 형태의 위키 링크를 만든다. 하지만 에이전트의 파일 읽기 도구나 GitHub 웹 화면에서는 [문서이름](./path/file.md) 같은 표준 마크다운 상대 경로 링크가 훨씬 정확하게 동작한다. 따라서 옵시디언 설정 → 파일 및 링크에서 ‘새 링크 형식’을 파일에 대한 상대 경로로, ‘Wikilinks 사용’을 OFF로 꺼두는 것을 추천한다.
  2. 1파일 1주제 + 고유 ID(REQ-001, ERR-001) 붙이기: 문서 하나에 수백 줄을 몰아넣기보다 주제별로 파일을 쪼개고, 요구사항이나 트러블슈팅 항목마다 고유 ID를 붙여둔다. 그러면 나중에 에이전트가 문서 전체를 다 읽지 않고 ERR-001 키워드만 검색해 필요한 단락만 쏙 뽑아 읽을 수 있어 토큰과 시간을 크게 아낄 수 있다.
  3. activeContext.md는 50줄 이내로 가볍게 유지하기: 인수인계 문서에 과거에 끝난 일까지 다 쌓아두면 점점 무거워진다. 현재 단계 / 방금 완료한 일 / 다음 할 일 / 주의사항 4가지만 50줄 이내로 유지해야 새 세션을 열었을 때 에이전트가 맥락을 가장 빠르게 파악한다.
  4. 결국 사람도 직접 열어보고 읽어보기: 에이전트가 문서를 자동으로 정리해 주더라도, 가끔씩 옵시디언을 열어 연결된 문서 구조가 맞는지, 잘못 적힌 스펙은 없는지 사람이 직접 눈으로 확인하는 습관이 있어야 문서 시스템이 엉키지 않고 오래 유지된다.
