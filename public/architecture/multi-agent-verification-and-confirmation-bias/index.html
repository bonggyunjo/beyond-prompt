1. 역할 분리(독립 세션)의 이유와 남는 의문#

구현을 담당하는 에이전트와 별개로 테스트·검증을 담당하는 에이전트를 두는 구조는 꽤 합리적인 접근이라고 생각한다. 각 에이전트가 독립적인 세션(컨텍스트)을 가지기 때문이다.

한 세션 안에서 구현부터 테스트까지 한 번에 처리하면, 에이전트가 자신이 작성한 코드의 의도와 가정에 갇히는 확증 편향(Confirmation Bias)이 생기기 쉽고 앞선 시행착오가 컨텍스트를 흐리게 만든다. 반면 새 세션에서 출발하는 테스트·검증 에이전트는 구현 과정의 변명을 모르는 백지상태에서 결과물만 놓고 보기 때문에 상대적으로 더 객관적인 시선으로 빈틈을 짚어낼 가능성이 높다.

하지만 여기서 자연스럽게 하나의 의문이 들었다.

“세션을 분리해서 정밀해졌다고는 하는데, 에이전트가 ‘검증 완료’라고 보고한 결과가 실제로 믿을만한 테스트와 검증인지 내가 어떻게 알 수 있을까?”

정해진 정답이 있는 영역은 아니고 사람마다 활용하는 방식도 다양하지만, 결국 테스트·검증 에이전트 역시 LLM이기 때문에 단순히 세션을 분리했다는 사실만으로는 신뢰성이 자동으로 보장되지 않는다고 본다. 구현 코드에 맞춰 느슨한 테스트를 역산해 짜거나, 어려운 부분을 Mock으로 덮어놓고 통과했다고 보고할 가능성은 여전히 남아 있기 때문이다.

2. 믿을만한 테스트·검증인지 판단하기 위해 내가 추천하는 5가지 기준#

내가 직접 에이전트를 다뤄보며 느낀 점들을 바탕으로, 검증 에이전트의 보고를 그대로 믿기보다 아래 다섯 가지 기준을 함께 확인하는 편을 추천한다.

① 요약 문장이 아니라 실제 실행 증거(Command & Exit Code) 확인하기#

*“단위 테스트와 통합 테스트를 모두 통과했습니다”*라는 텍스트 요약만으로는 판단하기 어렵다. 실제로 어떤 테스트 명령어를 실행했는지, 종료 코드(Exit Code)가 정상(0)인지, 전체 몇 개 중 몇 개가 통과했고 스킵(Skipped)되거나 완화된 검증 조건은 없었는지 원시 실행 로그를 함께 남기도록 유도하는 편이 좋다.

② ‘구현 코드’가 아니라 ‘요구사항 명세(Spec)‘를 기준으로 테스트하기#

검증 에이전트에게 구현 코드만 던져주고 *“이 코드 테스트해 줘”*라고 하면, 구현 코드의 현재 동작(심지어 버그까지)을 정답으로 삼아 테스트를 끼워 맞출 위험이 있다. 개인적으로는 구현 코드가 아니라 처음 합의한 요구사항 명세(PRD, API 스펙, 수용 기준)를 기준으로 테스트 케이스를 먼저 도출한 뒤 구현과 대조하도록 방향을 잡는 편이 훨씬 낫다고 느꼈다.

③ 정상 케이스(Happy Path) 외에 실패·경계값 케이스 포함하기#

정상 입력 1~2건만 통과하는 테스트로는 충분한 확신을 얻기 어렵다. 빈 값/null, 경계값, 권한 오류, 예외가 발생해야 정상인 실패 시나리오가 검증 목록에 들어 있는지 살펴보는 편이 좋다. 특히 버그 수정 작업이라면 수정 전 상태에서 테스트가 실제로 실패(Red)하는지 먼저 확인하고, 수정 후 통과(Green)로 바뀌는지 거치는 흐름을 추천한다.

④ Mock 사용 범위의 경계 살펴보기#

에이전트는 테스트 통과를 쉽게 만들기 위해 DB, 외부 연동, 핵심 의존성까지 과도하게 Mock으로 대체하려는 경향을 보이곤 한다. 전부 Mock으로 돌리면 실제 SQL 오류나 직렬화 문제, 트랜잭션 설정 누락은 걸러내기 어렵기 때문에, 어디까지를 Mock으로 두고 어디를 실제 통합 환경에서 검증했는지 리포트에 구분해 달라고 요청하는 것이 도움이 된다.

⑤ ‘구현 코드 전체’보다 ‘검증 체크리스트 + Diff’ 위주로 검수하기#

검증 에이전트가 뽑아낸 테스트 시나리오 목록만 사람이 훑어봐도 이 검증이 꼼꼼한지 대충 넘어갔는지 어느 정도 감이 온다. 조금 더 확실히 확인하고 싶을 때는 코드에 의도적으로 작은 버그를 하나 심어두고 검증 에이전트가 실제로 잡아내는지 확인해 보는 방식(변이 테스트 관점)도 꽤 유용하다.

3. 일회성 프롬프트로 끝나지 않으려면: 계층적 .md 문서 구조 활용하기#

위와 같은 기준들을 머리로만 기억하고 매번 채팅창에 길게 프롬프트로 적어주는 방식은 금방 지치기 쉽다. 특히 검증 에이전트를 독립적인 새 세션으로 띄우면 이전 대화에서 내가 강조했던 테스트 기준을 전혀 기억하지 못한 채 기본 상태로 출발하게 된다.

그래서 내가 체감상 가장 추천하고 싶은 방식은, 계층적 문서 구조 안에 테스트·검증 전용 .md 파일(예: docs/testing-policy.md 또는 계층별 AGENTS.md 규칙)을 두고, 에이전트가 검증 단계에 들어갈 때마다 해당 문서를 읽고 정해진 절차대로 수행하도록 흐름을 잡아두는 것이다.

[계층적 문서 구조 예시]
├── Root 지침 (AGENTS.md / 시스템 규칙)
│     └─ "구현 완료 후 독립 검증 단계로 넘길 때, 테스트 관련 .md 문서를 먼저 읽고 절차를 따를 것"
│
└── 테스트·검증 규칙 문서 (test-guide.md / verification.md)
      ├─ 1. 구현 코드가 아닌 요구사항(Spec) 기준으로 테스트 시나리오 작성
      ├─ 2. Happy Path + 실패/경계값 케이스 포함 여부 점검
      ├─ 3. Mock 사용 범위 명시 및 통합 테스트 실행 여부 기록
      └─ 4. 실제 실행 명령어, 통과/실패 건수, Exit Code 원시 결과 보고

물론 에이전트를 활용하는 정답이 하나로 정해져 있는 것은 아니지만, 이렇게 테스트 관련 .md 파일을 계층 구조 속에 배치하고 각 테스트·검증 프로세스 절차를 문서대로 따라가게 구성해 두면, 매번 사람이 똑같은 지시를 반복하지 않아도 어떤 세션의 에이전트가 들어오든 내가 기대하는 기준에 가까운 검증 결과를 얻을 수 있다고 본다.
