1. 실험: 아무런 UI/UX 프로세스 없이 에이전트에게 프론트를 맡겨보았다#

roomora 프로젝트를 진행하며 백엔드와 프론트엔드를 빠르게 구축해 보았다. 사실 프론트엔드도 명확한 기준과 프로세스를 갖춰야 완성도가 나온다는 건 당연한 이야기지만, 일부러 하나의 실험을 해보고 싶었다.

“에이전트에게 아무런 UI/UX 매뉴얼이나 디자인 프로세스 없이, 기능 구현 지시만 던졌을 때 프론트엔드를 어느 수준까지 뽑아낼까?”

결론부터 말하면 처참했다. 말 그대로 “딱 기능만 돌아가는 정도"였다. 구현을 마치고 화면을 띄우자마자 두 가지 문제가 곧바로 눈에 들어왔다.

  1. UI/UX가 전반적으로 너무 촌스럽다.
  2. 키워드, 문구, 색감까지 전반적으로 ‘AI가 만든 티’가 너무 강하게 난다.

백엔드는 아키텍처나 계층 구조, API 스펙, 테스트 규칙만 잘 잡아줘도 어느 정도 일정한 품질이 나온다. 반면 프론트엔드는 시각적 위계나 사용자 흐름, 여백 규칙, 문구 톤을 지정해 주지 않으면 에이전트가 흔한 기본 템플릿 감성으로 화면을 채워버리기 때문에 체감 완성도가 급격히 떨어졌다.

결국 프론트엔드 역시 설계 문서에 UI/UX 매뉴얼과 프로세스를 명확히 넣어 지시해야 완성도 있게 만들 수 있다는 결론에 다다랐다.

2. 프론트엔드 UI/UX 설계 매뉴얼에 넣어야 할 핵심 기준#

앞으로 에이전트에게 프론트엔드 작업을 맡길 때, 설계 문서에 아래 기준들을 기본 매뉴얼로 고정해 두고 지시하려 한다. 크게 UX/디자인 사고의 4가지 원칙과 에이전트 제어를 위한 실전 규칙으로 나눌 수 있다.

① ‘왜(Why)‘와 맥락(Context), 그리고 정보 구조(IA) 잡기#

단순히 기능 버튼을 화면에 배치하는 것이 아니라, 사용자가 이 화면에 들어오기 직전과 직후의 상황을 먼저 정의한다.

  • 사용자 의도 파악: *“버튼을 누른다”*가 아니라 *“급하게 처리해야 해서 불안한 마음으로 화면을 본다”*처럼 감정과 상황을 먼저 짚어준다.
  • 정보 위계(Hierarchy)와 화면별 단일 목적: 한 화면에 모든 기능을 다 때려 넣지 않도록 전체 페이지 흐름(IA)과 화면마다 단 하나의 핵심 행동(Primary Action)을 먼저 정해준다. 사용자가 가장 먼저 봐야 할 1순위 정보만 강조하고 부차적인 요소는 과감히 덜어낸다.

② 디테일의 완성: 엣지 케이스, 폼 UX, 마이크로 인터랙션#

정상적인 화면(Happy Path)만 그리는 것과 실사용 가능한 화면을 만드는 것의 차이는 예외 상태에서 드러난다.

  • 다양한 상태 설계: 데이터가 없을 때(Empty State), 로딩 중일 때(Skeleton UI), 에러가 났을 때(Error State), 텍스트가 예상보다 길어질 때의 화면 처리를 빠짐없이 설계한다.
  • 폼과 피드백 규칙 통일: 입력 검증 시점(onBlur vs onSubmit), API 요청 중 버튼 중복 클릭 방지(disabled + 로딩 상태), 사소한 알림(Toast)과 중요 확인(Modal)의 구분, 클릭 시 즉각적인 시각 피드백까지 기준을 통일해 둔다.

③ 일관성과 시스템적 사고: 레퍼런스, 디자인 토큰, 그리고 금지 목록#

화면마다 버튼 모양이나 여백 규칙이 다르면 사용자는 무의식적으로 피로감을 느낀다. 특히 에이전트에게 “모던하고 깔끔하게” 같은 추상적인 형용사를 주면 결과물이 들쭉날쭉해지기 쉽다.

  • 레퍼런스 + 디자인 토큰 고정: 참고할 서비스의 무드(예: Linear, Toss, Notion 등)와 함께 Primary/Surface/Border/Muted Text의 HEX 컬러, 폰트, 여백(예: 8px 그리드), border-radius 수치를 미리 고정한다.
  • ‘하지 말아야 할 것(Forbidden)’ 명시: AI 특유의 티를 지우는 데는 금지 목록이 가장 효과적이다. 과한 네온 그라데이션, 카드 안의 카드 중첩(Card-in-Card), 제목마다 붙이는 이모지 아이콘(대신 단일 아이콘 라이브러리로 통일), 요청하지 않은 가짜 통계 배지 삽입 등을 명시적으로 금지한다.
  • UX Writing(카피라이팅): “오류 코드 404” 같은 딱딱한 시스템 용어나 AI스러운 상투어 대신, *“페이지를 찾을 수 없어요. 홈으로 이동할까요?"*처럼 사용자의 다음 행동을 안내하는 자연스러운 문장을 쓰도록 기준을 준다.

④ 반응형 레이아웃과 구현 후 브라우저 검증#

구현이 끝났다고 바로 완료 처리하지 않고, 실제 렌더링 결과까지 검증 흐름에 포함시킨다.

  • 반응형 규칙 명시: 최대 컨텐츠 폭(예: 1080px 등)과 모바일(375px) 기준에서 내비게이션과 테이블이 어떻게 변형되어야 하는지 미리 적는다.
  • 시각 검증 + 사용자 관찰: 코드 작성 후 데스크톱과 모바일 뷰포트에서 직접 화면을 띄워 콘솔 에러나 레이아웃 깨짐이 없는지 확인하게 하고, 이후 실제 사용성 테스트(UT)와 이탈·클릭 지표를 보며 가설을 다듬는다.

3. 한눈에 보는 기준: 표면적인 UI vs 깊이 있는 UI/UX#

에이전트에게 프론트엔드 작업을 지시하거나 결과물을 검수할 때, 아래 표의 기준을 체크리스트로 삼으면 훨씬 완성도를 끌어올릴 수 있다고 본다.

구분표면적인 UI (아쉬운 경우)깊이 있는 UI/UX (지향점)
기획 단계예쁜 레퍼런스부터 찾아 따라 그림사용자 여정 지도(User Journey)와 화면별 단일 목적 먼저 작성
시각 규칙추상적인 형용사로 지시해 AI 감성 노출디자인 토큰(색상/여백/폰트)과 금지 목록(Anti-Pattern) 명시
상태 관리데이터가 가득 찬 정상 화면만 제작빈 화면, 로딩, 에러, 중복 클릭 방지까지 모두 설계
텍스트‘확인’, ‘취소’, ‘입력하세요’ 등 기계적 표현사용자의 다음 행동을 유도하는 명확한 UX 라이팅
수정 기준“이 색깔이 더 예쁜 것 같아서”“사용자가 이 버튼을 3초 안에 찾지 못해서”

결국 에이전트가 “기능만 돌아가는 화면"을 넘어 사람이 쓰기 편한 인터페이스를 뽑아내게 만들려면, 프론트엔드 역시 감에 기대지 않고 이런 기준들을 설계 문서와 매뉴얼에 먼저 박아두는 프로세스가 필수라고 느꼈다.
