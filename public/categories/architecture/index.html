AI 에이전트와 함께 옵시디언(Obsidian)을 효율적으로 사용하는 방법: 폴더 구조, 권한, 그리고 AGENTS.md 설계

1. 옵시디언(Obsidian)이란 무엇이며, 왜 에이전트와 함께 쓸까? 옵시디언(Obsidian)은 클라우드 서버에 데이터를 저장하는 일반 웹 노트 앱(노션 등)과 달리, 내 컴퓨터 로컬 폴더에 저장된 순수 마크다운(.md) 파일들을 그대로 읽어 화면에 보여주고 연결해 주는 로컬 지식 관리 도구다. 처음에는 일반 메모장이나 노션과 무엇이 다른지 헷갈릴 수 있지만, AI 에이전트와 함께 개발할 때 옵시디언을 쓰는 이유는 매우 분명하다. 로컬 .md 파일과의 일체형 구조 (사람과 에이전트의 공용 작업대): 에이전트는 웹 브라우저를 뒤지는 것보다 내 로컬 폴더 안의 .md 파일을 직접 읽고 수정하는 데 훨씬 빠르고 정확하다. 옵시디언은 그 로컬 .md 파일들을 그대로 띄워주는 뷰어 겸 에디터 역할을 하므로, 사람은 깔끔한 노트 화면으로 보고 에이전트는 원본 텍스트 파일을 바로 읽고 쓰는 공용 공간이 된다. 여러 프로젝트를 잇는 중앙 허브 (SSOT) 및 지식 재사용: 백엔드 코드 저장소와 프론트엔드 코드 저장소가 나뉘어 있어도, 두 저장소가 하나의 옵시디언 보관함(Vault)을 함께 바라보게 구성하면 문서의 단일 진실 공급원(SSOT)이 만들어진다. 또한 프로젝트가 하나 끝나더라도 그 과정에서 쌓은 기술 노트와 트러블슈팅 경험, 에이전트 작업 규칙을 다음 프로젝트에서 그대로 재사용할 수 있다. 세션이 바뀌어도 유지되는 기억과 토큰 절약: 새 채팅 세션을 열 때마다 프로젝트 배경을 길게 다시 설명할 필요 없이, 잘 나뉜 옵시디언 문서 중 지금 작업에 필요한 .md 파일만 에이전트가 골라 읽게 만들 수 있다. 2. 효율적인 폴더 구조: 공통 참조 / 프로젝트 / 트러블슈팅 나누기 옵시디언 보관함(Vault) 안에 모든 파일을 섞어두면 사람도 찾기 어렵고 에이전트도 엉뚱한 문서를 읽게 된다. 개인적으로는 역할에 따라 공통 참조 영역, 개별 프로젝트 영역, 트러블슈팅·기록 영역으로 폴더를 나누어 관리하는 구조를 추천한다. ...

멀티 에이전트 구조에서의 테스트·검증, 그리고 확증 편향에 대한 해결 방법

1. 역할 분리(독립 세션)의 이유와 남는 의문 구현을 담당하는 에이전트와 별개로 테스트·검증을 담당하는 에이전트를 두는 구조는 꽤 합리적인 접근이라고 생각한다. 각 에이전트가 독립적인 세션(컨텍스트)을 가지기 때문이다. 한 세션 안에서 구현부터 테스트까지 한 번에 처리하면, 에이전트가 자신이 작성한 코드의 의도와 가정에 갇히는 확증 편향(Confirmation Bias)이 생기기 쉽고 앞선 시행착오가 컨텍스트를 흐리게 만든다. 반면 새 세션에서 출발하는 테스트·검증 에이전트는 구현 과정의 변명을 모르는 백지상태에서 결과물만 놓고 보기 때문에 상대적으로 더 객관적인 시선으로 빈틈을 짚어낼 가능성이 높다. ...
